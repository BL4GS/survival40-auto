# Survival40 — ConoHa WING 復旧手順と本番更新の判断基準

最終確認: 2026-10-12。**手順書であって、実際のリストアや本番更新を行った記録ではない。**

## 0. 本番サイトの更新前の観測値
- WordPress の Survival40 Auto: 有効、v0.19.20。GitHub Release `latest` と `version.txt` も v0.19.20。
- 投稿: 公開23件・下書き16件（予約投稿0件）。ゴミ箱56件は管理画面で確認済み。
- 記事の自動運転・一般記事の自動公開: ともにOFF。アフィリエイト告知と出典表示: ON。フロントエンド広告の新スイッチは未設定で、デフォルトOFF。
- ConoHa WING の自動バックアップ画面: 2026-10-11の Web・DB・Mail が「リストア可」。**復元実験の成功記録はない。**
- 旧版 v0.19.20 ZIP は GitHub Actions で退避・検査済み。公開記事ID/URL/本文ハッシュの更新前記録も保存済み。

## 1. 障害発生時は原因と復旧範囲を切り分ける
1. 変更を止め、記事の自動投稿やプラグイン連続更新を始めない。アクセス状況・エラー・時刻を記録。
2. 管理画面に入れるなら、最初に Survival40 Auto の有効状態・バージョンと、公開23件/下書き16件の差異を確認。
3. **プラグイン単体**の問題なら、**旧版プラグインのみ**に戻す。記事やDB全体を過去へ戻してはいけない。
4. WordPress全体のファイル消失・DB破損が確認された場合に限り、ConoHa の Web/DB復元を別途検討する。

## 2. 第一選択: v0.19.20 へのプラグイン単体の復旧
- GitHub Actions 旧版ZIP退避の実績: https://github.com/BL4GS/survival40-auto/actions/runs/38210856074
- 厳密な v0.19.21 → v0.19.20 のWP-CLI隔離復旧成功: https://github.com/BL4GS/survival40-auto/actions/runs/38216906095
- WordPressが使える場合は、旧版ZIPによるプラグイン再インストールで対象ディレクトリのみ戻す。実行前にZIPとインストール先が Survival40 Auto であることを確認する。
- WordPress管理画面が使用不能なら、ConoHaファイルマネージャー/FTPで `/public_html/ドメイン名/wp-content/plugins/survival40-auto/` のみを対象に復旧を検討。上書きの前に現在のフォルダを退避し、**他のプラグイン・uploads・テーマ・wp-config.php は触らない**。
- 復旧後は PHP エラー・サイト表示、プラグイン有効/0.19.20、公開23件/下書き16件、記事自動運転OFFと自動公開OFF、ナビゲーターの画像を照合。
- これは隔離環境で実施済みだが、**ConoHa実機上での復旧実績ではない**。

## 3. 第二選択: ConoHa自動バックアップからWebデータだけ取り出す
- コントロールパネル → WING → サーバー管理 → 自動バックアップ → 対象日付の **Web** の「リストア可」を選ぶ。対象サーバー・ドメイン・時点を必ず確認。
- ConoHa の公式説明では、リストアで作られたファイルは `/home/cXXXXXXXX/backup_data_web` 配下に配置される。これは**本番のWebファイルを自動で全て巻き戻す操作ではない**。
- 正しいドメインの保存先（例: `/home/cXXXXXXXX/backup_data_web/public_html/ドメイン名`）を確認し、必要な個別ファイルのみ、ファイルマネージャーかFTPで対象の公開ディレクトリにコピーする。
- 復元ファイルは**24時間後に削除**され、再リストアすると以前の復元ファイルは削除される場合がある。週5回以上のリストアには制限がある。現場での復旧予定・作業者の時間が確保されるまで押さない。
- 公式: https://support.conoha.jp/w/restorebackup/ 、https://support.conoha.jp/w/recovery-web/

## 4. 最終手段: ConoHaデータベースの復元
- ConoHa の DB リストアは、復元対象日付を識別できる**別のデータベース**を生成する。復元操作だけでは WordPress の利用先DBは切り替わらない。
- 公式手順では、対象 WordPress の `wp-config.php` の DB 名・ユーザー・認証情報等を変更して利用先を切り替える。**設定ファイルや認証情報をチャット/GitHubへ貼らない。**
- DBを古いものへ切り替えると復元時点以降の記事・下書き・設定を失う可能性がある。通常のプラグイン更新失敗への対処としては実施しない。
- 公式: https://support.conoha.jp/w/recovery-db/ 、https://support.conoha.jp/w/wpconfigurationfile/

## 5. 本番アップデートの承認条件
- 本番に適用する必要のあるコードはまず隔離環境で検証する。v0.19.21の更新・逆戻しはテスト済み。
- **ConoHa WebとDBの復元可能性は、運用に影響しない複製環境での実測など、独立した検証を済ませること。** 「リストア可」の表示だけでは承認しない。
- 更新前のプラグイン・記事・広告設定を再取得し、ConoHaバックアップと旧版ZIPが残っていることを確かめる。
- 監視・復旧対応できる人がいる時間帯にのみ、GitHubのガード付き明示的リリースを実施。リリースの認証文字列を確認なしに形式的に入力しない。
- 更新後、WordPressでプラグイン版/有効状態・記事数・OFF設定を直接確認。公開23件の比較には `production-article-compare.yml`（基準run `38210094227`）を利用する。
- 既存のページレイアウト、記事、栞さんの画像、広告の有効状態を変更しない。差異が出たら適用を停止し、旧版ZIPへのプラグイン限定復旧を優先。
