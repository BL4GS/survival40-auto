# Survival40 — 最短完成ルート (2026-10-12)

**目的:** 記事ごとの人手による承認・ZIP導入に戻さず、広告なしでもAIが自律的に企画・調査・執筆・公開・停止判断できる最小運用を最優先で稼働させる。広告・販売連携は運営の必須条件としない。

## 何が実装済みか
- 公開版 v0.19.20: WordPress内に既存の記事企画、ソース探索・本文照合、Gemini記事生成、品質・安全レビュー、非YMYLの条件付き自動公開、WP-Cron定期実行が実装済み。**ただし本番設定 `auto_enabled=0`, `auto_publish_general=0`; したがって現時点で実運用されていない。** OFFのため `survival40_auto_cron` がCron一覧に存在しないことも2026-10-12に確認済み（正常なOFF状態）。
- v0.19.21: 保護されたリリース候補。公開記事23件+下書き16件に合わせた模擬データで既存v0.19.20→候補→v0.19.20の隔離アップグレード・復旧に成功。**未配布。**
- v0.19.22候補: 改善された誤企画のfail-closed処理、管理者専用の企画キューと既存の調査・生成への引渡しを隔離WordPressで試験済み。**未配布、外部キューは下書き作成止まりで未公開。**
- GitHub側: 週次Gemini企画→分類/品質検査→WordPress向け未調査企画JSON生成済み。送信は既定OFF、WordPress企画受信エンドポイントは次期版のみ。
- WordPressの正規URLは `https://www.survival40.com`。以前の企画配達コードが `https://survival40.com` を指していたため、HTTP転送を拒否する認証保護仕様と衝突する問題をPR #21で修正・単体テスト済み。**外部配送自体が本番で稼働したという意味ではない。**
- サイト内Shiori/栞の画像・表示、23公開/16下書き、全既存レイアウトを維持する。

## 臨界工程: 同時並行で実施

### A. 本番稼働に必須
1. ConoHaの実際のWeb/DB復元を、記事を失わない隔離複製等で検証する。リストア可表示では不十分。認証やホスティング側の操作が必要な場合のみ所有者へ**まとめて**依頼。実サイトのDBを巻き戻して試験しない。
2. 復元成功・プラグイン旧版ZIP・公開/下書きの現況・OFF設定・監視可能時間が揃ってから、v0.19.21の公開を明示的に承認して実施。勝手に4項目のリリース保護をすり抜けない。
3. **広告なしの自律記事**を先に小規模稼働。WordPress内の既存Gemini調査・レビュー・YMYL holdと非YMYL公開ゲートを使う。初回は同時公開の大量生成を禁止。発行された記事はソースの信頼性・独自価値・事実誤認・重複を実測し、不備があれば自動運転停止。
4. 失敗ログ・重複回避・Cron実行、記事品質、Shiori表示、記事数/リンクを実測。適用後は旧版に戻せる状態を維持。

### B. 開発側は並行して前進
1. 既存のWordPress記事生成経路を再利用し、外部の週次企画キューは追加の候補供給口に限定。記事作成システムを二重開発しない。
2. v0.19.22の企画受信・研究・下書き試験を継続。**企画キューからの自動公開は、外部未調査の入力を直接通さない追加ゲートを別途設計・検証する。**
3. WordPress Application Password（GitHub Secrets保管）や週次企画配送は、本番受信プラグインの導入後にのみON。GitHubの接続権限/Secretが使用できなければ、WordPress内ネイティブ企画機能でMVPを進めて外部連携待ちをクリティカルパスにしない。
4. Amazon/A8などの商用商品情報/審査/価格/掲載権限は**未検証なら広告ゼロ**。無理に貼り付けず、MVP稼働後に段階導入。
5. 自動公開後の更新・リンク保守・SEOフィードバックはMVP実測後に強化する。

## 「完成」の判定を分ける
- **第一段階（最短MVP）:** サイトが人手なしに非YMYL・広告なしの有益記事を適切な根拠と編集審査のもとで継続公開でき、根拠不足・品質不合格・API障害時は停止。所有者は日々の原稿承認をしない。
- **第二段階（全体完成）:** 自動企画供給・独立調査・広告照合・自動公開・記事更新/リンクメンテナンス・運用監視が継続的に働く。外部プロバイダ制限のため実測前に「完成」とは言わない。
- **進捗の数値化:** 「CIで成功」≠「本番で動作」。処理件数/自動公開数/品質失敗率/障害検知/復旧成功を別々に記録。

## 更新禁止条件
- ゆうが本業中で復旧対応できず、監視担当もいない。
- ConoHa Web/DBの復旧手段が未検証、または最新バックアップが確認できない。
- 自動公開の最小品質ゲートを再検証できない。
- 過去記事・栞さんの表示や広告のOFF設定の維持を確認できない。

**重要:** 本資料は最短化の実装・判断順序。自動的な本番更新・広告ON・本番復元の許可書ではない。
